# 00 — البرومبت الرئيسي لتنفيذ مشروع AyahX (ابدأ من هنا)

أنت مهندس برمجيات أول تعمل على مستودع **AyahX** (منصة صانع ريلز القرآن والابتهالات).
ستنفّذ **خطتين مرتبطتين** موجودتين بجوار هذا الملف:

| الملف | المحتوى |
|---|---|
| `01_DATA_PLAN.md` | القراء والسور والنصوص والتوقيتات والصوت (مصادر QUD) + تكامل الـ Aligner + ربط الريندر |
| `02_ADMIN_PLAN.md` | لوحة الأدمن الكاملة بكل أقسامها وربطها بالموقع |

اقرأ الملفات الثلاثة كاملة قبل كتابة أي سطر كود.

---

## 1. قواعد العمل (إلزامية)

1. **ابدأ بالفحص لا بالكتابة.** المرحلة 0 في كل خطة هي جرد للكود الحالي (قراءة فقط). لا تفترض وجود جدول أو ملف أو endpoint قبل أن تفتحه بنفسك. ملف `AGENTS.md` نفسه يقول إن هذا الـ checkout مستقل عن worktree إعادة بناء الأدمن، فلا تفترض أن migrations الأدمن موجودة. حدّد أولاً أي فرع/worktree فيه ماذا.
2. **مرحلة واحدة في كل مرة.** لا تبدأ مرحلة قبل أن تنجح كل اختبارات القبول للتي قبلها. بعد كل مرحلة اكتب تقريراً بالعربية (الصيغة في القسم 5).
3. **لا شيء وهمي.** ممنوع: بيانات تجريبية تُعرض كأنها حقيقية، أزرار لا تفعل شيئاً، إعدادات تُحفظ ولا يقرؤها أحد، `try/catch` يبتلع الخطأ، نجاح مزيّف.
4. **لا بناء على التخمين في بنية المصادر الخارجية.** كل بند مكتوب في الخطتين بعلامة **[تحقّق]** يعني أنني لم أستطع رؤيته بنفسي، وعليك فحصه فعلياً (تحميل عيّنة حقيقية) وتسجيل النتيجة في `docs/data-audit.md` قبل الاعتماد عليه.
5. **قواعد AGENTS.md سارية:**
   - مخرجات الذكاء الاصطناعي **ليست** نص قرآن معتمداً ولا توقيتاً معتمداً أبداً.
   - الاعتماد (credentials) على السيرفر فقط، لا في `VITE_*` ولا في اللوجات ولا في Git.
   - اختيار المزوّد صريح؛ ممنوع fallback صامت لمزوّد آخر أو إرسال ملفات خاصة بدون موافقة.
   - الحفاظ على RTL والعربية وتشكيل القرآن والتصميم الحالي.
   - ريندر/صوت/توقيت: التحقق يكون بفحص الناتج الفعلي، ليس بنجاح `build` ولا `/api/health` فقط.
   - النشر (deploy) عملية منفصلة لا تقم بها إلا بأمر صريح.
6. **التزم بالتصميم الحالي للموقع** في الأدمن (قسم التصميم في `02_ADMIN_PLAN.md`). لا تخترع هوية بصرية جديدة.
7. **كل ميزة تُسلَّم بثلاثة أشياء:** كود + اختبار + دليل تشغيل فعلي (لقطة/مخرج أمر/ملف ناتج). بدون الدليل لا تقل "تم".
8. **ما لا يمكنك إنجازه** (مثلاً مفتاح API غير موجود، أو سيرفر المصدر لا يستجيب): قلها صراحة في التقرير واترك الميزة في حالة "معطّلة بوضوح" بدل تقليدها.

## 2. ترتيب التنفيذ (الاعتماديات)

```
D0 جرد البيانات ─┬─> A0 جرد الأدمن
                 │
D1 النص والسور ──┤
D2 كتالوج القراء ┤
D3 استيراد التوقيتات
D4 طبقة الصوت (AudioResolver)
                 │
A1 أساس الأدمن (RBAC + تصميم + audit)  ← يمكن أن يبدأ بعد D1
A2 مكتبة القرآن في الأدمن (سور/قراء/تلاوات)  ← بعد D2
A3 مركز الاستيراد + التوقيتات ← بعد D3
D5 تكامل الـ Aligner ─> D6 مراجعة واعتماد التوقيت ─> D7 ربط الريندر ─> D8 ربط الواجهة
A4..A12 بقية أقسام الأدمن (مستخدمون، اشتراكات، ريندر، خلفيات، ...)
D9 / A13 تصليب نهائي وأداء وأمان
```

ابدأ فعلياً بـ: **D0 و A0 معاً** (قراءة فقط) ثم أرسل تقرير الجرد قبل الانتقال لأي كتابة.

## 3. المهارات المتاحة في `.agents/skills` وأين تستخدمها

اختر ما يناسب المهمة فقط (لا تشغّل الكل في كل مهمة):

| المرحلة | المهارات |
|---|---|
| تخطيط وتقسيم | spec-driven-development, planning-and-task-breakdown, incremental-implementation |
| أي خلل | systematic-debugging, debugging-and-error-recovery |
| واجهات الأدمن | ui-ux-pro-max, frontend-ui-engineering, accessibility |
| الجودة والأداء | web-quality-audit, core-web-vitals, performance, seo, code-review-and-quality |
| قبل إعلان الانتهاء | verification-before-completion |
| اختبارات المتصفح | `e2e` (انظر `docs/e2e-guide.ar.md` و `tooling/e2e`) |
| فهم البنية | terrain-knowledge-skill (الكود الحالي له الأولوية على أي وثيقة مولّدة) |
| الذكاء الاصطناعي | use-ai-sdk (الـ gateway الموجود في السيرفر هو حدّ التكامل في الإنتاج) |

الوكلاء الفرعيون المتوازيون تحتاج إذناً صريحاً حسب قواعد البيئة؛ لا تفترضه.

## 4. تعريف "تم" لأي مرحلة

- [ ] كل بنود القبول في المرحلة محققة بدليل.
- [ ] `npx tsc --noEmit` و `npm run lint` و `npm test` تمر.
- [ ] اختبارات المرحلة الجديدة مكتوبة وتمر، ولا يوجد اختبار قديم تعطّل.
- [ ] migration قابلة للتشغيل مرتين دون خطأ (idempotent) ولها rollback موثّق.
- [ ] لا مفاتيح/أسرار في الكود أو اللوج.
- [ ] تحديث `docs/` و `FEATURE_QA_LOG.md` بما تغيّر.
- [ ] تقرير المرحلة أُرسل.

## 5. صيغة تقرير نهاية كل مرحلة (بالعربية)

```
## تقرير المرحلة <الرمز> — <الاسم>
1. ما الذي تغيّر (ملفات/جداول/endpoints)
2. ما الذي تحققت منه فعلياً (أوامر + مخرجات/لقطات)
3. نتائج الاختبارات (عدد/نجاح/فشل)
4. ما لم يكتمل أو يحتاج قراري، وسببه
5. المخاطر المعروفة
6. الخطوة التالية المقترحة
```

## 6. ما تفعله إذا اختلف الواقع عن الخطة

الكود الحقيقي يغلب الخطة. إذا وجدت تعارضاً: وثّقه في `docs/data-audit.md` (أو `docs/admin-audit.md`)، اقترح تعديلاً صغيراً على الخطة، وانتظر الموافقة قبل توسيع النطاق.
