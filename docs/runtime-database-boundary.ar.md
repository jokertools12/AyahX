# فصل تشغيل التطبيق عن تعديل قاعدة البيانات

تقرأ API وخدمتا Skia/control مخطط قاعدة البيانات قبل بدء العمل. لا تنشئ
هذه المسارات الجداول أو الأعمدة، ولا تحاول إصلاح مخطط ناقص أثناء التشغيل.
تعيد `/api/health/ready` الحالة 503 إذا تعذر الاتصال أو غاب عمود مطلوب.

الفحص عقد وجود لأعمدة 31 جدولًا في النسخة المهاجرة، وليس بديلًا للتحقق من
الأنواع والقيود والمفاتيح وaudit triggers باستخدام تقارير المهاجرات. يقرأ
`information_schema.COLUMNS` فقط، ويجمع الطلبات المتزامنة ويخزن النجاح لعشر
ثوانٍ. الفشل لا يُخزَّن، فتُعاد المحاولة بعد توفر قاعدة البيانات.

بدء API وفحص readiness يشتركان في تهيئة واحدة قابلة لإعادة المحاولة. لا تبدأ
مؤقتات صيانة الرندر أو الاحتفاظ بالمحاذاة قبل نجاح الفحص. إنشاء كائن الطابور
وحده لا يبدأ مؤقتات؛ الإيقاف يزيلها. يحتفظ control بدورات الصيانة الخاصة به.

قراءة الإعدادات تحافظ على أولوية القيم المخزنة وفك التشفير والرجوع لمتغيرات
الخادم. انتقال الأسرار القديمة إلى التخزين المشفر يستخدم UPDATE مشروطًا كما
كان سابقًا، دون إنشاء جداول أو استيراد مهاجرة ضمن مسار القراءة.

## ترتيب التشغيل والترحيل

1. حدد البيئة والنسخة وقاعدة البيانات، واحفظ نسخة احتياطية حديثة واختبر
   استعادتها والترحيل على قاعدة منفصلة قبل تطبيق تغيير المخطط الحي.
2. شغّل `npm run db:setup` صراحةً في عملية منفصلة بمتغيرات `MYSQL_*` الخاصة
   بهوية المهاجرات. يتضمن الآن تحضير render/plan/settings/alignment الذي كان
   يعمل عند بدء الخدمات. يحتفظ بسلوك ترقية البيانات وسياسات التنظيف السابقة؛
   لا تشغله لمجرد فحص الاتصال. لا تضع هوية المهاجرات في إعداد التطبيق الدائم.
3. شغّل مهاجرات Enterprise 001 و002 بأوامرها المستقلة وتقارير backup/restore/
   rehearsal المطلوبة. `db:setup` لا يتجاوز هذه البوابات ولا يهيئ owner.
4. تحقق من المخطط والبيانات والتقارير، ثم استخدم هوية runtime محدودة لتشغيل
   API وSkia/control. أزل `npm run db:setup` من pre-deploy قبل نشر هذه الهوية.
5. تحقق من SUCCESS والنسخة الفعلية وreadiness والواجهة والرندر؛ نجاح فحص
   الأعمدة وحده لا يثبت صلاحيات DML أو قبول الرندر.

يجب أن تفتقد هوية التطبيق صلاحيات CREATE/ALTER/DROP/INDEX/TRIGGER وإدارة
الحسابات وGRANT OPTION. audit يقبل SELECT/INSERT فقط، والمنح تقبل تحديث عمودي
الإلغاء فقط دون تغيير هوية المنحة. اختبر القيود باستخدام هوية runtime فعلية،
واحفظ تفاصيل المنح والبيانات السرية في تقارير خاصة.

هذا الفصل البرمجي لا يغيّر المستخدمين أو المنح في MySQL أو إعدادات Railway
تلقائيًا. حتى تبديل الهويات وإزالة pre-deploy والتحقق من الخدمات الثلاث، تظل
بوابة عزل الصلاحيات قبل production غير مكتملة.
