# تشغيل حسابات قاعدة البيانات للخدمات

هذه الأداة تجهّز حسابًا جديدًا لخدمة واحدة على مخطط محدد. لا تغيّر حسابًا قائمًا، ولا تُشغّل ترحيل المخطط، ولا تبدّل إعدادات اتصال التطبيق. نجاحها على قاعدة تجريبية لا يعني أن حسابًا حيًا استُخدم أو أن الخدمة نُشرت.

## الصلاحيات المخططة

يجب أن يطابق المخطط 31 جدولًا قبل أي إنشاء للحساب أو منح للصلاحيات. ينشئ المخطط 31 منحة صريحة على مستوى الجدول، مع `mandatory_roles` فارغة. الحساب الجديد يُفحص بدخول مستقل عبر `CURRENT_USER()` و`CURRENT_ROLE()` و`SHOW GRANTS` ثم مقارنة كل نقطة صلاحية بالخطة.

- 24 جدولًا قديمًا: `SELECT/INSERT/UPDATE/DELETE` للتوافق الحالي. هذا حد توافق أعلى، وليس أقل صلاحية مثبتة لكل خدمة؛ يجب تقليصه بعد جرد عمليات الكتابة لكل API وSkia وcontrol.
- خمسة جداول كتالوج غير مفعلة: `SELECT` فقط.
- جدولا السلطة: API يقرأ ويضيف سجل التدقيق، ويقرأ المنح ويضيفها ويحدّث حقلي الإلغاء فقط. Skia وcontrol للقراءة فقط.
- لا تمنح الخطة `CREATE` أو `ALTER` أو `DROP` أو `TRUNCATE` أو `TRIGGER` أو صلاحيات حسابات أو صلاحية على مخطط التطبيق الآخر.

## المتطلبات قبل التشغيل

يجب أن يوفّر المشغّل المصرّح له مدخلًا خاصًا جديدًا بصيغة JSON يحتوي `target` بالحقول `environment`, `host`, `port`, `serverUuid`, `schema`, `version`؛ وحقول `user`, `service` (`api` أو `skia` أو `control`), `reason`, `requestId`, و`authorizationReferenceSha256`. يجب أن يطابق الهدف فعليًا البيئة والمضيف والمنفذ وUUID وإصدار MySQL والمخطط.

عيّن `ENTERPRISE_RUNTIME_ENVIRONMENT` صراحةً إلى `local` أو `staging` أو `production`. عند التشغيل على Railway يجب أن يطابق `RAILWAY_ENVIRONMENT_NAME`. تحتفظ خدمة MySQL ببيانات المشغّل/الجذر منفصلة. المسار المقصود هو حقن `ENTERPRISE_RUNTIME_DATABASE_URL` إلى عملية SSH مؤقتة لمرة واحدة بعد تحميل بيانات MySQL من مخزنها الخاص؛ لا يوجد TCP proxy. هذا المسار لم يُتحقق بعد بعد cutover. لا تحفظ بيانات المشغّل في متغيرات API أو worker أو control، ولا تضف URI إلى Git أو وسيطة أمر أو سجل. استخدم مخزن أسرار/ملفًا محميًا عند الحاجة لتمريره إلى عملية SSH.

استخدم مجلدًا خاصًا بصلاحيات وصول للمشغّل وحده. جهّز ملف المدخل الخاص مسبقًا. يجب أن تكون مسارات التقرير وملف الاعتماد جديدة؛ ترفض الأداة استبدال ملفات الإخراج الموجودة. راجع ACL في Windows أو صلاحيات المجلد في Linux قبل التشغيل. لا تحفظ الملفات في Git أو artifacts العامة.

## فحص الخطة ثم التطبيق

من جذر المشروع، استخدم المسارات الخاصة الجديدة المناسبة للبيئة:

```powershell
$env:ENTERPRISE_RUNTIME_ENVIRONMENT = 'staging'
# حمّل ENTERPRISE_RUNTIME_DATABASE_URL من مخزن الأسرار دون طباعته.
node node_modules/tsx/dist/cli.mjs scripts/enterprise-runtime-principal.ts `
  --input <private-input.json> --out <private-inspection.json>
```

راجع تقرير الفحص والهدف وعدد الجداول/المنح. للتطبيق، استخدم مدخلًا وتقريرًا وملف اعتماد جديدًا، وأضف `--apply --credentials <private-credentials.json>`. الأداة تولّد كلمة مرور جديدة وتكتبها في ملف الاعتماد الخاص قبل إنشاء الحساب، ثم تدخل بها وتتحقق من المنح الفعالة. لا تُعرض قيمة كلمة المرور ولا تُلصق في إعدادات الإنتاج قبل إجراء تغيير منفصل ومراجع للخدمة.

```powershell
node node_modules/tsx/dist/cli.mjs scripts/enterprise-runtime-principal.ts `
  --input <new-private-input.json> --out <new-private-report.json> `
  --credentials <new-private-credentials.json> --apply
```

الأداة تشترط اسم حساب جديدًا و`mandatory_roles` فارغة، وتستخدم advisory lock، وتتحقق من تطابق الهدف ومن مخطط الجداول. أي فشل بعد بدء إنشاء الحساب قد يترك حسابًا أو منحًا جزئية لأن DDL والمنح تثبت تلقائيًا في MySQL؛ التقرير يذكر `incomplete` و`inspectBeforeRetry`. **لا تعاود الأمر عميانيًا ولا تحذف الحساب أو المنح آليًا.** افحص الحالة والمنح الفعلية أولًا ثم اتبع إجراء إصلاح مصرحًا ومراجعًا.

## بوابة النقل إلى الخدمات

التحقق على clone منفصل يثبت سلوك الأداة فقط. قبل تغيير إعداد أي خدمة، يجب إزالة أمر `db:setup` من pre-deploy، والتأكد أن API وSkia وcontrol لا تنفذ DDL عند البدء، وتوفير مسار ترحيل منفصل بامتيازاته المناسبة، ثم اختبار حسابات مستقلة على نسخة staging والتحقق من عمليات الخدمة ومنع DDL وتعديل/حذف سجلات التدقيق. انشر وتحقق من كل خدمة على حدة مع الاحتفاظ بمسار رجوع مضبوط. لا تغيّر الحساب الحالي أو بيانات الاتصال للإنتاج استنادًا إلى نتائج clone.
