# صلاحيات مكتبة Enterprise

هذه الطبقة مستقلة عن `user_roles` القديمة. حساب admin لا يصبح owner تلقائيًا،
ولا تُقبل الصلاحية من JWT أو جسم الطلب. يقرأ الخادم الحساب الموجود والمنح
وسجل التدقيق عند كل عملية. هذه الشريحة تدير المنح فقط؛ اعتماد المحتوى وتفعيل
المصادر وربط التصدير لم يكتمل بعد.

| الدور | الصلاحيات |
| --- | --- |
| read_only | الاطلاع |
| editor | الاطلاع وكتابة المسودات |
| approver | الاطلاع والاعتماد والرفض وسحب الاعتماد |
| owner | جميع ما سبق، وإدارة المنح والمصادر والاحتفاظ |

تتجمع صلاحيات الأدوار المتعددة. approver لا يكتسب كتابة المسودة ضمنيًا.
إلغاء منحة يوقف استخدامها فورًا؛ يبقى تاريخ العمليات التي أجازتها محفوظًا.
لا يمكن إلغاء آخر owner نشط أو حذف حسابه قبل منح owner لحساب نشط آخر.

## واجهة الخادم

كل المسارات تتطلب تسجيل الدخول وتعيد `Cache-Control: private, no-store`:

- `GET /api/catalog/access`: صلاحيات ومنح الحساب الحالي فقط.
- `POST /api/catalog/grants`: يتطلب `grant_manage`؛ الجسم يحوي `targetUserId`,
  `role`, `reason`, `requestId` فقط.
- `POST /api/catalog/grants/:id/revoke`: يتطلب `grant_manage`؛ الجسم يحوي
  `reason`, `requestId` فقط.

استخدم `requestId` نفسه لإعادة محاولة الطلب نفسه. إعادة استخدامه مع محتوى
مختلف تعيد 409. الإلغاء يحتفظ بالمنحة وسجلها، ولا يمسح تاريخها. تُكتب المنحة
وسجل التدقيق في transaction واحدة تحت قفل مشترك مع المهاجرات. فشل التدقيق
يُلغي العملية. لا يوجد مسار HTTP لتهيئة owner.

## تهيئة المالك مرة واحدة

تسبقها مهاجرات 001 و002 المراجعة مع backup وتجربة restore وتحقق البيئة.
يُشغَّل `scripts/enterprise-owner-bootstrap.ts` يدويًا بهوية DB مخصصة، بعد
تحديد صاحب الحساب صراحةً. لا يُشغَّل عند بدء التطبيق أو في CI.

يحتوي ملف الإدخال الخاص على `target` كاملًا: environment/host/port/serverUuid/
schema/version، و`expectedUserId`, `expectedEmail`, `authorizationReferenceSha256`,
`reason`, `requestId`. البصمة الأخيرة مرجع لتفويض المالك، وليست مفتاحًا أو كلمة مرور.
يقارن الخادم الحساب والهدف الفعليين، ويشترط فراغ جدولي المنح والتدقيق قبل
التهيئة الأولى؛ إعادة المحاولة المطابقة تعيد نفس النتيجة.

ضع رابط DB في متغير الخادم `ENTERPRISE_AUTHORITY_DATABASE_URL` فقط. تُقرأ البيئة
الموثوقة من `RAILWAY_ENVIRONMENT_NAME`، أو من `ENTERPRISE_AUTHORITY_ENVIRONMENT`
عند التشغيل الصريح خارج Railway. اختلافهما يوقف العملية، ولا يحدد ملف الإدخال
البيئة الموثوقة. لا تستخدم `VITE_*` ولا تضع بيانات الحساب أو الرابط في Git.

```powershell
npx tsx scripts/enterprise-owner-bootstrap.ts --input <private-input.json> --out <private-new-report.json>
```

يُحجز التقرير قبل الاتصال، ولا يُستبدل ملف موجود. التقرير الفارغ يدل على عدم
اكتمال العملية؛ لا يُعد دليل نجاح. احفظ الملفات في مكان خاص خارج الملفات المتتبعة.

قبل تفعيل الصلاحيات في production، يجب فصل حساب المهاجرات عن حساب التطبيق
وإزالة صلاحيات تغيير المخطط من التطبيق بعد فصل DDL التلقائي من startup/preDeploy.
وجود audit triggers مع حساب DB قادر على إسقاطها لا يحقق هذا الفصل.
